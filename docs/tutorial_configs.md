# Tutorial Configuration Profiles (v2.7.0)

**Final split-version note:** This document is aligned with the final modular XTQSPRKinetic v2.7.0 package, including generalized `target_cols`, optional Mordred descriptor parallelization, optional per-target Boruta parallelization, the optional XTQSPRKinetic explicit-H Mordred runtime patch, descriptive-figure outputs, Bootstrap/hybrid-routing quality gates, QDA feasibility checks, and the updated Mordred installation profiles generated by `gen_xtqspr_requirements.py`. Detailed installation guides are kept under `docs/setup/`.

This document explains the purpose and recommended use of the two tutorial configuration files provided with XTQSPRKinetic:

- `configs/tutorial.yml`
- `configs/tutorial_auto.yml`

These files are intended for **learning, demonstration, and reproducible example runs**. They are fully commented and designed to expose key XTQSPRKinetic features without requiring users to build a configuration from scratch.

For normal/public tutorial runs, the v2.7.0 Diagnostic Audit module is disabled by default:

```yaml
diagnostics_enable: false
diagnostics_random_controls_mode: off
```

Enable diagnostic-audit outputs only in a separate manuscript/diagnostic configuration.


The final split package also exposes conservative Bootstrap/hybrid-routing and QDA-feasibility safeguards. These should remain visible in tutorial configs because they explain why a requested hybrid run may safely fall back to soft or hard routing, and why an infeasible `lda+qda` Auto-Chooser candidate may be skipped.

```yaml
bootstrap_use_for_soft_routing: false
bootstrap_use_for_hybrid_routing: true
bootstrap_quality_gate_enable: true
bootstrap_min_median_modal_vote: 0.65
bootstrap_max_median_norm_entropy: 0.55
bootstrap_min_hard_fraction: 0.05
bootstrap_max_hard_fraction: 0.95
bootstrap_sampling_mode: bootstrap

qda_feasibility_gate_enable: true
qda_min_class_count: 5
qda_auto_skip_infeasible: true
```

## 0. Environment and Mordred-profile recommendation

For Python 3.13 environments, the recommended clean route is to use the community-maintained Mordred distribution while keeping the same code import path:

```bash
python gen_xtqspr_requirements.py ./src ./main \
  --xtqspr-defaults \
  --pin none \
  --profile py313-both \
  --out-dir .
```

This produces both Mordred routes:

- **Recommended clean Python 3.13 route:** `mordredcommunity` with NumPy 2.x compatibility.
- **Legacy original-Mordred route:** `mordred==1.2.0` with a documented compatibility override.

Store the generated installation guides in:

```text
docs/setup/INSTALL_PY313_MORDREDCOMMUNITY.md
docs/setup/INSTALL_PY313_ORIGINAL_MORDRED_LEGACY.md
```

For the clean route, install using the generated `requirements-all-py313-mordredcommunity.txt`. The code still uses:

```python
from mordred import Calculator, descriptors
```

The legacy original-Mordred route is kept for reproducibility, but may report a `pip check` metadata conflict if `drfp` requires NumPy 2.x while the legacy Mordred workflow forces NumPy 1.26.4. Use the legacy route only after runtime validation.

## 1. v2.7.0 target-column behavior

XTQSPRKinetic v2.7.0 generalizes the target layer. The tutorial profiles retain the default Arrhenius case study:

```yaml
target_cols: ["lnA", "n", "Ea"]
```

To demonstrate a different continuous reaction-property problem, add the relevant numeric target columns to the input CSV and set `target_cols` accordingly, for example:

```yaml
target_cols: ["Ea_forward", "Ea_reverse", "delta_H_rxn"]
```

The tutorial profiles are intended for continuous supervised regression targets. Classification labels, temperature-dependent curves, and structured outputs require separate task-specific logic.

## 2. Runtime acceleration settings in tutorial configs

The final v2.7.0 split code separates Mordred descriptor parallelization from Boruta feature-selection parallelization.

### Mordred descriptor parallelization

```yaml
mordred_parallel_enable: false
mordred_parallel_n_jobs: -1
mordred_parallel_backend: loky
mordred_parallel_batch_size: auto
```

Use `mordred_parallel_enable: true` when descriptors must be regenerated for a larger dataset. If `descriptor_cache: true` and a valid cache exists, Mordred descriptors are loaded from cache and the parallel computation is not triggered.

### Per-target Boruta parallelization

```yaml
boruta_parallel_enable: false
boruta_parallel_targets_enable: true
boruta_parallel_n_jobs: -1
boruta_parallel_backend: loky
boruta_parallel_inner_n_jobs: 1
```

Use `boruta_parallel_enable: true` when `boruta_per_target: true` and multiple targets are configured. Keep `boruta_parallel_inner_n_jobs: 1` during outer Boruta parallelization to avoid CPU oversubscription.

For tutorial runs, it is acceptable to keep both parallel flags disabled for maximum reproducibility and easier log interpretation. For larger demonstration runs, enabling both can reduce runtime without changing the scientific output.

### Optional XTQSPRKinetic explicit-H Mordred runtime patch

For radical-rich C/H tutorial or validation datasets, the final v2.7.0 code can enable a controlled runtime patch for Mordred/MordredCommunity descriptor calculation:

```yaml
mordred_xtqspr_explicit_h_patch_enable: false
```

Use `false` for standard Mordred/MordredCommunity behavior. Use `true` only when the tutorial or research dataset intentionally requires the explicit-Hydrogen-aware modified descriptor mode for species such as `CH4`, `[CH3]`, `[CH2]`, `[CH]`, `[H]`, and `[H][H]`.

When this mode is enabled, use a fresh descriptor cache or disable cache reuse for the first run:

```yaml
descriptor_cache: false
```

When reporting results from this mode, describe the descriptors as **XTQSPRKinetic explicit-hydrogen-aware modified Mordred/MordredCommunity descriptors**.

## 3. `tutorial.yml` (fixed, feature-rich demo)

`tutorial.yml` is the recommended starting point for first-time users who want to see a **single, controlled XTQSPRKinetic run** with rich outputs enabled.

### What it demonstrates

- A **fixed family-discovery setup** such as `lda`, `lda+fcm`, or another configured method
- Generalized target handling through `target_cols`
- Optional SHAP-based explainability outputs
- Optional descriptive-figure outputs, when enabled
- Bootstrap stability artifacts, where enabled, without forcing Bootstrap probabilities into soft routing unless explicitly configured
- Hard, soft, or hybrid routing behavior, according to the config, with Bootstrap quality gates protecting hybrid routing when enabled
- Reproducible run-level outputs in a dedicated output folder
- Optional Mordred/Boruta runtime acceleration controls
- Optional explicit-H Mordred runtime-patch control for radical-rich C/H examples

### When to use it

Use `tutorial.yml` when you want to:

- learn the pipeline structure,
- inspect output artifacts,
- test that your environment is working correctly,
- generate an example run for documentation/screenshots,
- understand how a **fixed** non-auto configuration behaves.

### Typical command

```bash
python main/main.py --config configs/tutorial.yml
```

## 4. `tutorial_auto.yml` (auto-chooser demonstration)

`tutorial_auto.yml` is designed specifically to demonstrate XTQSPRKinetic's **Auto-Chooser** workflow, meaning automatic family-discovery strategy selection/evaluation.

### What it demonstrates

- `family_selection_mode: auto`
- Auto-evaluation of candidate family-discovery strategies
- Comparison-driven method selection under a tutorial-friendly setup
- Lightweight screening behavior relative to fully exhaustive manuscript settings
- Tuning-safe behavior in which expensive post-hoc outputs can be disabled during preliminary candidate evaluation
- Clean skipping of statistically infeasible QDA candidates before QDA covariance fitting

### When to use it

Use `tutorial_auto.yml` when you want to:

- demonstrate or test **automatic configuration/method selection**,
- compare auto-selection behavior against a fixed tutorial run,
- teach users how XTQSPRKinetic can choose among candidate family-discovery methods.

### Typical command

```bash
python main/main.py --config configs/tutorial_auto.yml
```

## 6. Recommended learning sequence

For new users, the suggested order is:

1. Install dependencies using the appropriate Mordred profile for the Python environment.
2. Run **`tutorial.yml`** first to understand the standard pipeline outputs.
3. Then run **`tutorial_auto.yml`** to observe how automatic selection changes the workflow and outputs.
4. Compare the generated output directories to understand which artifacts are run-specific versus selection-specific.
5. Enable SHAP, descriptive figures, diagnostics, parallel settings, or the explicit-H Mordred runtime patch only after confirming that the base tutorial run works.

## 7. Bootstrap/hybrid-routing and QDA tutorial behavior

Tutorial configs should keep Bootstrap use conservative for normal users. The recommended behavior is:

```yaml
bootstrap_replace_family_labels: false
bootstrap_retrain_on_replaced: false
bootstrap_use_for_soft_routing: false
bootstrap_use_for_hybrid_routing: true
bootstrap_quality_gate_enable: true
```

This allows Bootstrap to provide stability diagnostics and, when explicitly requested, quality-gated hybrid routing, without silently changing normal soft routing.

For tutorial Auto-Chooser runs that include `lda+qda`, keep the QDA gate enabled:

```yaml
qda_feasibility_gate_enable: true
qda_min_class_count: 5
qda_auto_skip_infeasible: true
```

If LDA creates a very small family, the QDA candidate is skipped rather than producing a low-level covariance error. This is expected and should be described as a data-feasibility decision, not as a pipeline crash.


## 8. Descriptive-figure and SHAP behavior

The tutorial profiles may expose SHAP and descriptive-figure settings, but these can be computationally expensive.

For lightweight tutorial or auto-chooser runs:

```yaml
shap_sample_size: 0
descriptive_figures_enable: false
```

For final interpretability/reporting runs:

```yaml
shap_sample_size: 100
descriptive_figures_enable: true
```

When descriptive figures are enabled, v2.7.0 can generate outputs such as:

- PCA reaction-family landscapes
- target-colored landscapes for each configured target
- residual-colored landscapes for each configured target
- descriptor-signature heatmaps
- descriptor boxplots by learned family
- reaction-level routing probability heatmaps
- family-level median routing probability heatmaps

The family-level median routing heatmap is a cleaner summary companion to the reaction-level heatmap and is useful for manuscript or Supporting Information interpretation.

## 9. Diagnostic-audit settings

The tutorial profiles are normal/public configurations. They keep the v2.7.0 Diagnostic Audit module disabled by default:

```yaml
diagnostics_enable: false
diagnostics_random_controls_mode: off
```

For diagnostic-audit or manuscript-reproducibility runs, create a separate configuration and enable:

```yaml
diagnostics_enable: true
diagnostics_random_controls_mode: size_matched
diagnostics_random_controls_n: 25
```

The `size_matched` random-control mode preserves the learned-family size distribution while destroying the chemical relationship between reactions and learned families.

## 10. Runtime-output and logging notes

The final v2.7.0 code can report detailed stage timings and total run time. Depending on the current logging/timing patch applied in your codebase, the run output may include:

```text
run_runtime.json
run_runtime_summary.csv
```

These files provide a compact record of the total configuration runtime, selected topic method, target columns, and relevant parallelization flags. They are useful for comparing tutorial, auto-chooser, and manuscript runs.

## 11. Notes for maintainers

- Keep `tutorial.yml` focused on a **stable, reproducible, pedagogical example**.
- Keep `tutorial_auto.yml` focused on **Auto-Chooser demonstration**, not maximum accuracy.
- Keep `target_cols` visible because it defines the supervised reaction-property targets.
- Keep `mordred_parallel_*`, `boruta_parallel_*`, and `mordred_xtqspr_explicit_h_patch_enable` visible because these are final v2.7.0 public config controls.
- Keep `diagnostics_enable: false` in public tutorial configs unless the file is explicitly a diagnostic/manuscript profile.
- If default paths change, update the example commands in this file, `README.md`, and `docs/run_guide.md` together.
- If requirements-generation behavior changes, update this file together with `README.md`, `docs/run_guide.md`, and the generated setup guides under `docs/setup/`.
- Keep installation guide links pointed to `docs/setup/`, while requirement `.txt` files remain at the repository root.
- Keep Bootstrap routing-control keys and QDA feasibility keys visible in both tutorial configs so users can understand quality-gated hybrid routing and clean QDA candidate skipping.
- If new configuration keys are added in future versions, preserve full comments in both tutorial files so they remain useful as learning references.
